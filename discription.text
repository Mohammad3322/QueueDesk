19. Project Purpose and Business Context
    QueueDesk is a browser-based customer-support operations application for a small SaaS company. The company currently manages customer issues using spreadsheets, email, and informal communication between support agents. QueueDesk replaces that fragmented workflow with a centralized operational interface.
    The project intentionally focuses on frontend engineering rather than backend complexity. The learner should spend most of the work on application state, data transformations, reusable components, forms, validation, TypeScript modeling, API boundaries, responsive design, accessibility, testing, performance, and explicit system-design decisions.
    1.1 Business Problems to Solve
    • Tickets are missed or forgotten.
    • Urgent requests are not consistently prioritized.
    • Ownership is unclear.
    • SLA deadlines are missed.
    • Managers cannot quickly understand team workload.
    • Historical tickets are difficult to search.
    • Support metrics are weak or unavailable.
    • Workflow rules are inconsistently applied.

    Each layer must have a clear responsibility. Do not create architectural layers simply to make the diagram look sophisticated.
    5.6 Data-Flow Exercise
    Read Path — Load Tickets
    User opens /tickets → page requests data → ticketService.getTickets() → request → response → data stored → search/filter/sort/paginate → rows rendered
    Write Path — Change Ticket Status
    User changes status → validate action → enter updating state → ticketService.updateTicket() → success/failure → update authoritative state → append activity event → UI rerenders
    For every write flow, explicitly document the failure path. The learner should be able to explain what remains on screen, whether retry is appropriate, and whether rollback is needed.
    5.7 Component Boundary Thinking
    TicketDetailPage ├─ TicketHeader ├─ TicketDescription ├─ TicketProperties ├─ CustomerSummary ├─ CommentList ├─ CommentComposer └─ ActivityTimeline
    Use responsibility rather than arbitrary file size as the primary decomposition criterion. Ask whether separation improves comprehension, reuse, testing, or ownership. Avoid both giant components and micro-components with no meaningful responsibility.
    5.8 Client-Side vs. Server-Side Responsibility
    For this portfolio implementation, search, filtering, sorting, and pagination may be client-side. The system-design document must explain when these operations would move to the backend, especially once ticket volume makes loading all records unreasonable.

    Browser → GET /tickets?status=open&page=2&sort=dueAt → server/database filters and paginates → compact response
    5.9 Failure Design
    • Tickets fail to load.
    • Ticket update fails.
    • Customer data is missing.
    • Comment submission fails.
    • Request times out.
    • Invalid ticket ID is opened.
    • Older async response arrives after a newer one.
    For every failure mode define: what the user sees, whether existing data remains usable, whether retry is available, and whether the system retries automatically or waits for explicit user action.
    5.10 Performance Design
    Before optimizing, write hypotheses. Example: sorting 10,000 tickets on every unrelated render may cause input lag. Later validate hypotheses with profiling. Do not use memoization, virtualization, or debouncing simply because they are known performance techniques.
    5.11 Security Boundary Thinking
    Hiding a button is not authorization. QueueDesk may hide manager controls for agents, but a production backend must independently enforce permissions. The learner must explicitly document the trust boundary between browser and backend.

    Search, filters, sorting, and pagination should be encoded in URL search parameters where practical. Example: /tickets?status=open&priority=critical&sort=dueAt&page=2. This makes the view shareable and resilient to refresh/back/forward navigation.

    10.3 Service/Data Layer

     18.3 Final Educational Principle
     The project is complete only when the learner can explain and defend the important decisions. During implementation, repeatedly ask: Why does this state exist? Why does it live here? Why is this component separate? Why is this an effect? What happens when this request fails? What happens when the dataset becomes large? What happens on mobile? What happens without a mouse?
